# 项目描述

> 本文只讲**主项目本身**：它是条什么链路、素材卡在哪一环、那些渲染约束**从哪来**。
> **本能力是什么** → `references/capability.md`。两者互不越界。

## 1. 链路

```
HTML 素材  →  常驻隐藏 WebView2（上位机内嵌，离屏）  →  CDP 轮询截屏  →  RGB565  →  像素差分
            →  只推变化区域  →  USB（LIVE 协议）  →  佳点 V1P / V2 的 RGB565 小屏
```

- **常驻**：上位机启动渲染会话时建一个**隐藏的 WebView2 窗口**（Tauri 内嵌，`visible(false)`），
  页面一直活着；素材就是「一块跑在这个隐藏浏览器里的面板」。
- **抓帧**：WebView2 **不支持 CDP `Page.startScreencast`**，实际实现是**轮询 `Page.captureScreenshot`**
  （PNG）。抓屏节奏两档：高刷 33ms≈30fps / 普通 100ms≈10fps；连续 **3 帧**画面没变化就降到 300ms（~3fps），
  一有变化立刻回目标档位。**抓屏不等于推帧**：画面没变时差分结果为空，USB 一个字节都不发。
- **差分与下发**：首帧 / 强制整屏用 LIVE `mode 0`（全帧）；之后按脏矩形用 `mode 1`（单块）
  或 `mode 2`（≤6 块批量）。`mode 3`（LZ4）协议保留但**上位机未启用**。
  USB 回执只有 `ok` 才更新差分基线；超时/异常会清基线、下一帧整屏重发。
- **与官方 GUI 共存**：上位机通过 `POST http://127.0.0.1:8765/usb/handoff/*` 借 USB 使用权
  （租约 120s、每 20s 续期），不用退出官方上位机。
- 设备是 RGB565 小屏；素材只负责画面，数据经本地 API 注入（见 `api_map.md`）。

## 2. 素材卡在哪一环

素材 = 链路的**最上游**：它决定"画面长什么样、动多少像素"。
上游写错，问题会在最下游（屏上）才暴露 —— 而且和链路 bug 长得一样，很难分。

所以素材必须**在进链路之前**就自证合规：这正是 `capability.md` 那套判据存在的原因。

## 3. 渲染约束从哪来

| 约束 | 来源 |
|---|---|
| 视口**锁死 `W×H`**、贴左上、禁居中 | 抓帧就是抓固定视口；页面自己居中/缩放会让差分基准漂移 |
| **每帧变化面积要小** | 差分后要经 USB 推，变化面积 = 带宽 = 流畅度。**唯一性能杠杆** |
| **不依赖 GPU 合成** | 面板跑在**隐藏/离屏** WebView2 里（CLI 预览路径甚至带 `--disable-gpu`）——
`backdrop-filter` 一类模糊效果不保证生效，还可能把重绘面积拖大 |
| **RGB565** | 设备色深低：1px 浅色细线会丢；亮饱和色当文字色普遍对比度不够 |
| **字号 / 对比度下限** | 屏小、像素密：10px 中文笔画会粘连，对比度不足直接看不清 |
| **单文件** | 素材要能独立投放与版本管理，不能带本机路径 |
| **数据可注入** | 上位机只做注入（`data-slot` / `__setSlot`），不解析素材的图形信息 |

## 4. 实机参数

| 项 | 值 |
|---|---|
| 支持尺寸 | **320×240（V2）** 与 **320×170（V1P）**，素材按 `assets/<主题>/v1p/`、`assets/<主题>/v2/` 分目录存放 |
| 当前常用实机 | **320×240（V2）**（本轮优化/验收主要围绕它；320×170 同样在用，公共逻辑尺寸参数化） |
| 主题形态 | 一个主题 = 一个目录，**HTML 与本地底图同层**；每个尺寸一个变体（个别主题只有一种尺寸） |
| 设备能力验证 | 需用户明确同意后才动真机（占 USB 句柄、改设备画面） |
| 数据/单位 | 见 `references/metrics.md`；面板取数关系见 `references/api_map.md` |

## 5. 与能力的关系

本能力**只碰素材**：不启设备、不抓帧、不差分、不下发。
它把上面这些项目约束，翻译成**可机检的判据**（见 `capability.md` §5），
让素材在进链路之前就把问题挡住。
